# Варианты концепций приложения

Документ отвечает на вопрос: **что реально можно построить**, имея только агента
Cursor, доступ к ИИ и аккаунт на GitHub — и чтобы это опиралось на
[исследования](research/), а не на фантазию.

Постановка задачи — в [`research/00-postanovka-zadachi.md`](research/00-postanovka-zadachi.md).

---

## Ограничения, из которых исходим

| Ресурс | Что это значит на практике |
| --- | --- |
| Агент Cursor | Пишет и правит код, генерирует и проверяет содержимое карточек |
| ИИ | Генерация карточек из материала, но с обязательной проверкой (≈4,8 % галлюцинаций даже после оптимизации промптов) |
| Аккаунт GitHub | Бесплатный хостинг статики (GitHub Pages), хранение данных в репозитории, планировщик задач (GitHub Actions по расписанию) |
| Чего **нет** | Своего сервера, базы данных, платных сервисов, магазинов приложений |

Отсюда жёсткое архитектурное следствие: **бэкенда нет**. Всё, что нужно, —
либо статический сайт с локальным хранением, либо файлы в репозитории, либо
задачи по расписанию в GitHub Actions.

## Что обязано быть в любой концепции

Эти пункты не обсуждаются — они вытекают из доказательной базы:

1. Активное извлечение, а не просмотр. *(Dunlosky 2013; Roediger & Karpicke 2006)*
2. Интервалы считает планировщик FSRS, а не самописная формула. *(см. `research/03-algoritmy-povtoreniy.md`)*
3. Обратная связь после каждого ответа. *(Butler & Roediger 2008)*
4. Нет кнопки «знаю, больше не показывать». *(Kornell & Bjork 2008)*
5. Главная метрика — отсроченное удержание, а не «% верных сегодня».
6. У каждой карточки — ссылка на источник; ИИ-карточки проходят проверку. *(Khurana 2026)*

# Концепция A. Фабрика карточек для Anki

**Суть.** Не делать своё приложение для повторений вообще. Сделать репозиторий и
инструмент, который превращает учебный материал (лекции, главы, конспекты) в
качественные атомарные карточки и собирает готовую колоду `.apkg` для Anki.
Повторениями занимается Anki с включённым FSRS.

**Как работает**

1. Исходники в репозитории: `sources/` — тексты, `decks/*.yaml` — карточки в
   виде обычных текстовых файлов (вопрос, ответ, источник, тема, тип).
2. Агент Cursor по фиксированному промпту-шаблону делает черновики карточек.
3. Второй проход — автоматическая проверка: один ли факт в карточке, есть ли
   ссылка на источник, нет ли утверждения, которого нет в исходнике.
4. Человек ревизует изменения через обычный pull request.
5. GitHub Actions собирает `.apkg` (например, через `genanki`) и публикует его
   в релизах репозитория.

**Плюсы**
- Максимальное соответствие исследованиям при минимуме кода: планировщик,
  мобильные клиенты, синхронизация, статистика уже существуют и отлажены.
- Вся ценность вкладывается туда, где она действительно создаётся, — в качество
  карточек. Именно там работают ИИ и ревизия.
- Версионирование колоды и история правок бесплатно, средствами git.

**Минусы**
- Нет «своего приложения» как продукта: пользователь учится в Anki.
- Нужно освоить Anki.

**Объём работы.** Наименьший из всех вариантов. Это скрипты и промпты, а не
приложение.

**Кому подходит.** Если цель — «выучить медицину надолго», а не «сделать
приложение». С точки зрения результата для студента это самый честный вариант.

# Концепция B. Своё веб-приложение на GitHub Pages (local-first)

**Суть.** Статический PWA на GitHub Pages: открывается в браузере телефона и
ноутбука, работает офлайн, данные хранятся локально в браузере, планировщик —
готовая библиотека FSRS.

**Как работает**

- Колода лежит в репозитории как обычные текстовые файлы и грузится в приложение.
- История повторений — в IndexedDB на устройстве.
- Синхронизация между устройствами: экспорт/импорт файла прогресса вручную либо
  запись в репозиторий через персональный токен GitHub, который пользователь
  вводит сам и который хранится только у него в браузере.
- Расписание считает библиотека FSRS из
  [open-spaced-repetition](https://github.com/open-spaced-repetition).

**Что можно сделать лучше, чем в Anki** (иначе вариант не имеет смысла):

- Интерфейс под конкретный медицинский материал, а не универсальный.
- Честная панель удержания: прогноз забывания и результаты **отсроченных**
  контрольных срезов вместо стриков.
- Встроенный режим «карточка → её источник в лекции» в один клик.
- Настройка целевой удерживаемости с явным предупреждением о росте нагрузки
  (по умолчанию 90 %, выше 97 % не рекомендуется — так же, как в Anki).

**Плюсы**
- Полный контроль над интерфейсом; ничего не надо устанавливать.
- Бесплатный хостинг и бесплатный домен вида `*.github.io`.

**Минусы**
- Всё, что в Anki уже сделано (синхронизация, статистика, отложенное
  расписание, надёжность хранения), придётся делать заново и хуже.
- Локальные данные в браузере можно потерять при очистке кэша — нужен продуманный
  экспорт.
- Риск переизобрести Anki без его качества.

**Объём работы.** Средний. Один разработчик с агентом сделает работоспособную
версию, но до уровня Anki по надёжности не доведёт.

# Концепция C. Spaced education: вопрос в день по расписанию

**Суть.** Повторить в виде бота/рассылки схему, которая в медобразовании
проверена рандомизированными исследованиями: короткий клинический вопрос по
расписанию, ответ, разбор.

Это единственная концепция, у которой есть прямое РКИ-подтверждение **именно в
таком формате доставки**: еженедельные письма с кейсом и вопросом значимо улучшали
результаты студентов через год, а у резидентов эффект детектировался через 2 года
(Kerfoot 2006, 2007, 2009).

**Как работает**

- GitHub Actions по расписанию (`cron`) раз в день берёт очередную порцию
  вопросов и отправляет их — например, через Telegram Bot API или почту.
- Ответ пользователя фиксируется, после ответа сразу приходит разбор с
  обоснованием и ссылкой на источник.
- Состояние повторений хранится в файле в том же репозитории и обновляется
  коммитом от Actions; интервалы считает FSRS.

**Плюсы**
- Самая сильная доказательная база среди всех вариантов для медицинского
  контекста.
- Не требует, чтобы пользователь «заходил в приложение»: материал приходит сам.
- Реализуется практически без интерфейса.

**Минусы**
- Пропускная способность низкая: 1–5 вопросов в день, это не инструмент для
  тысяч карточек перед сессией.
- Хранение прогресса в публичном репозитории — вопрос приватности; нужен
  приватный репозиторий.
- Зависимость от внешнего канала (Telegram/почта) и хранения секретов в
  GitHub Secrets.

**Объём работы.** Малый. Это скрипт плюс workflow-файл.

# Концепция D. Тренажёр клинического рассуждения

**Суть.** Шаг за пределы «термин → определение»: карточка — это короткая
клиническая виньетка, где нужно назвать диагноз, следующий шаг или трактовать
находку. Материал подаётся вперемешку по темам.

**Основание.** Мета-анализ переноса показал, что тестирование переносится сильнее
всего на вопросы на применение и вывод и **на задачи медицинской диагностики**,
но при условии совпадения формата тренировки с форматом применения
(Pan & Rickard, 2018). Карточки с определениями этот перенос не гарантируют.

**Важная оговорка.** Перемежение тем здесь надо делать **настраиваемым, а не
принудительным**: на ЭКГ-материале один эксперимент дал преимущество смешанной
практики (46 % против 30 %), другой — обратный результат на отсроченной проверке
(24 % против 34 % в пользу блочной). Данные противоречивы.

**Плюсы**
- Целится в то, ради чего материал и учится, — в применение.
- Отличается от Anki по существу, а не по оформлению.

**Минусы**
- Самое высокое требование к качеству содержания: клиническая виньетка,
  написанная ИИ без проверки специалистом, опасна.
- Медленное наполнение: виньетка дороже карточки на порядок.

**Объём работы.** Кода — средне, содержания — много.

# Концепция E. Линтер качества карточек

**Суть.** Не приложение для учёбы, а инструмент контроля: проверяет колоду
(свою или чужую, включая импортированную из Anki) и выдаёт отчёт о проблемных
карточках.

**Что проверяет**

| Проверка | Основание |
| --- | --- |
| В карточке больше одного факта | принцип минимальной информации (практика SuperMemo) |
| Ответ длиннее N слов / список без разбиения | то же |
| Нет ссылки на источник | требование к ИИ-контенту (Khurana 2026) |
| Утверждение не подтверждается указанным источником | проверка галлюцинаций |
| Вопрос допускает ответ узнаванием, без извлечения | Dunlosky 2013 |
| Дубликаты и взаимно интерферирующие формулировки | практика SuperMemo |

**Как работает.** CLI-скрипт плюс GitHub Action, который запускается на каждый
pull request с изменением колоды и оставляет комментарий с замечаниями.

**Плюсы**
- Точно попадает в главное узкое место — качество карточек.
- Полезен независимо от того, какая из концепций A–D будет выбрана.
- Маленький и хорошо проверяемый.

**Минусы**
- Часть проверок неизбежно эвристические; критерий «одна карточка — один факт»
  сам по себе экспериментально не доказан.
- Сам по себе ничему не учит.

**Объём работы.** Малый.

# Рекомендуемый порядок (если спросить моё мнение)

1. **E + A как база.** Сначала линтер качества и фабрика карточек: это даёт
   работающий учебный процесс за наименьшие усилия, потому что повторениями
   занимается уже отлаженный Anki с FSRS.
2. **C как надстройка.** Ежедневный вопрос по расписанию через GitHub Actions —
   дёшево и имеет самую прямую доказательную поддержку в медобразовании.
3. **D, если захочется дальше.** Переход от терминов к клиническому применению —
   единственное направление, где собственный продукт даёт то, чего в Anki нет.
4. **B — только осознанно.** Своё веб-приложение имеет смысл, если важен именно
   свой интерфейс и есть готовность вложиться; иначе это дорогой способ получить
   упрощённый Anki.

# Как проверять, что выбранное работает

Без этого любая концепция превращается в веру:

- Завести фиксированный набор контрольных вопросов, **не входящих** в
  ежедневные повторения.
- Прогонять его через 1, 3 и 6 месяцев. Сравнивать с исходным уровнем.
- Фиксировать реальные затраты времени в день.
- Не использовать как метрику успеха количество сделанных карточек, длину серии
  дней и процент верных ответов в текущей сессии — все три показателя
  систематически вводят в заблуждение (см. [`research/04-chto-ne-rabotaet.md`](research/04-chto-ne-rabotaet.md)).
